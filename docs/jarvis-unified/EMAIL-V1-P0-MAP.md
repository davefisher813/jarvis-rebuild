## Provider connection, token renewal, sync, checkpoints, status dimensions, worker heartbeat

The earlier substrate project built a solid on-demand foundation. Refresh tokens are AES-GCM encrypted per (user, email) in google_tokens (0018). api/google.ts has seven stable failure codes and a "durable means stored" connect, with 40+ tests. api/email/sync.ts does Gmail history sync with a cursor, 404 expiry resync, and freshness that advances only on success. Safe reads retry three times. Several accounts are isolated by per-account rows, and the client has offline and reauth banners. It does NOT meet the spec's "permanent connection" model in these ways. (1) Nothing runs without Dave's tap: no cron, pg_cron, watch, heartbeat, incident ledger or phone alert exists, and RELEASE-EVIDENCE explicitly records "No Vercel cron, no pg_cron". Everything in AC22-24 beyond a static banner, and AC41 worker silence, is missing. (2) The state model is one 3-value enum (connected/reauth/disconnected) plus last_sync_at and sync_error. There are no separate authorization/sync/send-health/device dimensions, no catching_up/stale/failed/storage_error states, and no verified_through_at or coverage window. (3) Sync fetches the newest 30 INBOX messages (no Sent, no 90-day window), advances last_sync_at after page 1, and never says "Catching up". (4) Real defects against AC37/38/40/41: revoked token is deleted then the account is mirrored as 'disconnected', which hides its cached mail from the inbox; accounts.ts and ensureAccount reset reauth to connected on every call; gmailFail maps Gmail 403 quota to PROVIDER_AUTH, which flips the account to reauth; the history loop silently stops at 20 pages and still advances the cursor; scopes are never persisted. Deploy hosting: verified from the repo, Vercel edge functions only, no crons config. Verified live: Vercel project jarvis-rebuild exists and its latest production deployment is READY. NOT verified: Vercel plan tier, and the JARVIS Supabase project (neither of the 2 projects visible to this session's Supabase connector has email_account, so extensions like pg_cron/pg_net could not be checked). A durable worker is therefore an assumption: candidates are Vercel Cron (plan-limited), Supabase pg_cron + pg_net or an edge function (needs enabling and a project check), or the existing Railway backend that already hosts web push.

## Send lifecycle and the 30-second server hold

Current hold duration: NONE. SEND_HOLD_MS, hold_until and dispatch_deadline do not exist anywhere in api/, src/ or migrations 0044-0054. The send is immediate. api/email/send.ts:57 calls send_approve, then in the same HTTP request (send.ts:69-75) runs runOutboxOnce, which claims, marks dispatched and POSTs to Gmail (_send.ts:134), then settles. The only time limits are the 5-minute review nonce (0046:582), a 5-minute "approved but unclaimed" cutoff (0050:434, 0046:721), a 2-minute claim lease (worker.ts:62) and a 20s Gmail timeout (_send.ts:17). There is no Undo after the tap, no countdown and no "Waiting to send" screen.

What is solid and reusable:
- Exact review with a single-use nonce and a hash over the snapshot, account and draft revision. Bcc and attachment sha256 are in the snapshot. The snapshot is built server-side from the draft row (send_review, 0050:280-367).
- Draft-row lock on approve. Two taps or two devices give one action (0050:386-401, proven in sends.sh:129-134).
- Outbox state machine: reviewed, queued, claimed, dispatched, confirmed, failed, outcome_unknown, cancelled (0046:31-32). Fenced claim: claim_token, lease, SKIP LOCKED. outbox_dispatched is the one-way mark and requires the token and an unexpired lease (0046:743-757). outbox_settle requires the token and turns a dispatched failure without a refusal code into unknown (0046:763-790).
- A throw, timeout, 5xx or 2xx without an id after the dispatched mark is outcome_unknown and is never retried. Blind retries are impossible: outbox_claim excludes unknown rows.
- Check Again reconciles by Message-ID search and confirms only on a hit. A miss proves nothing and Resend stays shut. Receipts are appended in the same function as the settle.
- command_cancel is already a row-locked compare-and-set that frees the draft (0050:494-532). It returns cancellation_requested "Already Handed to Gmail · Checking the Result" once claimed or dispatched (0046:677-681). That is the right foundation for Undo.

What a worker would need:
1. Migration 0055, additive: on outbox_command add hold_until, dispatch_deadline and approved_at. Add a paused_review_required state (the check constraint at 0046:31 must change). Add an unknown-reconcile schedule (next_check_at, check_attempts). command_approve sets hold_until = now()+30s and dispatch_deadline = hold_until+30s, and returns server_now. Put SEND_HOLD_MS = 30000 in one shared TS constant and mirror it in SQL.
2. Change outbox_claim and outbox_claim_action to claim only when hold_until <= now(). Past dispatch_deadline the row goes to paused_review_required and the draft is freed. That replaces the 5-minute APPROVAL_EXPIRED cancel branches (0046:721-725, 0050:434-438).
3. A real scheduler. vercel.json has only rewrites, .github/workflows/ci.yml is CI only, and nothing in the repo hosts a periodic job. Add a cron-authenticated route (for example api/email/dispatch.ts) that runs outbox_sweep, then runOutbox without an action filter, using dispatchFor(env), which already exists. The stranded queued/claimed sweep that RELEASE-EVIDENCE.md:633 deferred must be built here.
4. Stop dispatching inside the approve request. send.ts approves and returns the held command. The client polls draft_get or a getCommand route, which already exposes outbox_state.
5. Undo route: held to cancelled with the draft restored, plus new error codes UNDO_TOO_LATE, HOLD_EXPIRED and SEND_UNKNOWN. None of these are in src/substrate/commands/errors.ts. Undo must still work after countdown zero while the row is still queued.
6. Client: held screen with a server-time countdown, Undo, offline "Undo not confirmed. Reconnect to check", a first-use hold explanation, a paused Review reply path, and polling.
7. Cancel or pause undispatched commands when an account is paused, removed or disconnected, and on signout. Factor the reconcile logic into a shared function the worker can call on the 5s/30s/2m backoff.
8. Tests: the SQL proofs (sends.sh, commands.sh) are not run in CI (ci.yml has no reference to them). Port the new race, hold and deadline proofs somewhere CI runs them, or add the local-Postgres step.

Design risk to settle before building: dispatch_deadline = hold_until + 30s is tighter than a 1-minute cron. A cron-only worker would routinely miss the deadline and pause messages that should have sent. The worker needs sub-30s wake-up (an in-request delayed claim as the primary path with cron as the backstop, a persistent worker process, or pg_cron). Dave has to pick where it runs, because the spec's P0 exit asks for a verified environment that can host a durable hold worker.

## Capture to Tasks/Schedule/Money, candidates, ICS parser registry, five-state provenance, receipts view, agent context export and proposal paste import, capture intents

The commit-and-receipt core is built and solid: one atomic capture_approve call (migration 0046) writes the item, evidence, approval and receipt together, and double taps replay. Real-Postgres shell tests plus client tests cover it, and Undo, Dismiss and Restore work. Manual capture and module-not-ready both behave per spec. The shell tests (supabase/tests/*.sh) are not in CI. CI runs only tsc, eslint and vitest.

Four things are built against the spec:
- **Auto-detection.** Rule-based detection runs automatically on every loaded inbox row and every opened message (EmailFlow.tsx:262-295). It includes task and waiting templates, which spec 5.2 and AC11 ban, and bill/receipt templates, which the trim defers. Existing tests assert this behaviour, so they must be rewritten.
- **ICS parser.** It exists but breaks the 22.2 contract. It invents a 60-minute duration, takes the first of several events, and drops recurrence on edit. It cannot read all-day events, and it never sees real text/calendar parts or .ics attachments.
- **Provenance and parser registry.** Five-state provenance and the parser registry are absent. Each field has one flat provenance entry, and a user edit overwrites the extraction.

## RLS and ownership isolation, retention and purge, pause/remove/signout, event outbox, schema/version compatibility, accessibility and visual contract

Row-level isolation is the strongest part of what exists and is proven on real Postgres. Retention, purge, pause/remove/signout, the event outbox, the countdown accessibility and the efficiency measurement do not exist. Migrations 0044-0051 enable RLS on all 18 substrate tables (outbox_command included), revoke every browser grant, and use composite (id, owner_id) foreign keys. jarvis-core/supabase/tests/substrate.sh, sends.sh, commands.sh, candidates.sh, waiting.sh and email.sh prove A cannot read, write or approve B's rows (foreign ids answer NOT_FOUND).
