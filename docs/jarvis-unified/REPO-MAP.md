## 2. The universal item table, as it actually is

```
item(id uuid, owner_id uuid default auth.uid(), entity_type text -> entity_type(key), data jsonb, created_at, updated_at)
```

- `updated_at` is the row's revision: a trigger keeps it strictly increasing (0001). The app reads it as `serverTime` (epoch millis). Where the spec says `expected_revision` on an item, this repo means that instant.
- `entity_type` is a registry; an unregistered kind rejects every insert (`laws/entityRegistry.test.ts` holds the pair). 0044 registers `waiting` and `exploration_note`.
- RLS is `owner_id = auth.uid()` on every table, no shared rows anywhere (docs/ARCHITECTURE.md).
- Patches go through `item_apply_patch` (strips nulls, 0031) and `item_apply_patch_if_older` (offline age check, 0032).
- `replica identity full` and the realtime publication (0034): a row the server inserts reaches an open app through `src/data/realtimeSync.ts`.
- Idempotent creates: a unique index on `(owner_id, data->>'clientId')` (0039); both adapters resolve a second create with the same clientId to the first row.

Where the hash lives: the manifest hash a person approves is computed by `jarvis_context_shape` (sha256 over the manifest's jsonb text) and nowhere else, so the preview, the grant and the issue compare one number; the TypeScript canonical hash (`substrate/canonical.ts`) is for payloads the client builds (candidates, sends). ## 6. Deviations from the package, each with its reason

1. **Em dashes.** The package's Markdown carried 72 of them. The repo's house rule forbids any in a tracked text file (`qa/check.js`, and Dave's own rule), so each was written as a spaced hyphen on copy. Section ids and every other character are unchanged.
2. **Composite keys, Postgres 15 or newer.** The spec allows composite owner-aware keys or server checks; this build uses the keys. A set-null reference has to name its column, which Postgres 15 added. Supabase projects on 15 and 17 both run it; the local rehearsal ran on 16.
3. **Item revision is a timestamp.** `decision_dependency.expected_item_updated_at` and every `expected_revision` against an item carry `updated_at`, because that is the revision this repo has.
4. **A saved candidate may lose its destination.** When the item is later deleted the candidate keeps `status = 'saved'` with a null destination and the card says Item removed; the check only forbids a destination on a provisional candidate. Saved-means-written is enforced by the command function, not the constraint.
5. **Transactions and module writers.** The module writers are client-side (`Store` over PostgREST). The adapter's `prepare` produces exactly the record the writer stores and the contract tests hold the two equal; the command function of slice 03 inserts that record inside its transaction. No HTTP inside a transaction, no shadow Money table.
6. **Money's shape wins over the payload's.** Integer cents, two-decimal currencies only, no zero amount, no refund kind, no receipt number field. Each refusal keeps the candidate in Email with the field named. ADAPTER-CONTRACT.md lists them as Money's open questions.
7. **Events carry no zone.** `EventData` stores a local date and wall clock; a timed instant is written in the reader's zone, the way the mail appointment door already does. A span across midnight or more than one day stays in Email with Open in Gmail. Adding an optional zone field is a Schedule decision, flagged for slice 06.
8. **Copy follows the house style.** Rendered lines are Title Case fragments joined by a middle dot (the casing and short-copy laws), so "Money isn't ready. Your bill is still here." is "Money Isn't Ready · Your Bill Is Still Here". The meaning is the spec's; the shape is the app's.
9. **The fixed light palette.** Section 02's cream canvas and accents are not applied in this slice. The repo has one token system and a light-mode flip in flight on its own branch; slice 04 raises the palette with Dave before any new surface is drawn.
10. **Flags are a build variable.** `VITE_JARVIS_FLAGS` rather than a database switch, so a slice can land inert and be turned on per deploy without a migration.
11. **The logical idempotency key is the server's.** API-AND-VALIDATION.md asks for owner + action kind + candidate/draft version; `capture_approve` derives `capture:<candidate>:<revision>` itself, `action_undo` derives `undo:<action>`, and a send's key is its review nonce. The client's request id is recorded in the authorization snapshot and trusted for nothing. Two devices with the same card get the same action; a device with an older card gets IDEMPOTENCY_CONFLICT and the saved action's id.
12. **The review snapshot lives in the outbox.** `command_review` writes the exact payload into `outbox_command` in state `reviewed` and hashes it there (over the payload, the account, the kind and the draft revision), so the tap sends only the nonce and the hash it was shown, never the payload again; `command_approve` moves the row to `queued`. The spec's "immutable SendReview snapshot" is that row.
13. **Approval TTL, both halves.** A review nonce nobody taps lapses in five minutes (`approvals_sweep`, or the next tap). A tapped command that no worker dispatched within five minutes of the tap lapses at the claim with a receipt ("Not Sent · Approval Expired · Review It Again") rather than leaving late.
14. **Denied agent calls are receipts, coalesced.** Slice 02 answered a denial without a receipt; slice 03 adds `access_denied_record`, which the gateway calls after the ceiling refuses: who, which method, which code, never the params, one action per connection, method, code and hour (a repeat bumps the count). S02's "safe denied receipt" is that row.
15. **A capture of a record the module already holds creates nothing.** Money's fingerprint rule and an event's clientId make the same record once; the receipt says "Already in Money · ..." and the action is marked not created, so Undo refuses to remove a record the capture did not make.
16. **Erasure reaches the verb.** 0044 let an erasure blank the diff, scope, evidence and refs but not `exact_verb`; 0046 lets it set the verb to the one word Erased when `erased_at` is set, so a purged receipt carries no vendor, amount or address anywhere. The action's verb, key and hash become opaque tombstones too.
17. **The package's palette is scoped to the Hub.** Section 02's fixed light theme is applied as tokens on the Hub's root (`src/styles/hub.css`: cream canvas, white cards, dark text, the four accents and their tints, the 3px focus ring), so every shared component inside the Hub restyles through the tokens it already reads and nothing outside it changes; in dark mode the Hub is a light island, which the previews show in both themes for Dave to judge. One block to delete if he prefers the app's own tokens. The type ramp and radii stay the app's tokens (the type and casing laws).
18. **No verified adapter, so Add makes a manual assistant.** `connection_add_manual` makes a row with no token and no transport; its only exchange is export and import (H5). A Connect button that cannot connect is a false sign, so there is none; `agent_connection_verify` stays the server's door for a real adapter.
19. **A job is opened by the person.** `job_open` makes (or reuses) the one job per assistant and project when a project is picked for a preview or an import; the person's own export has a job with no assistant. Previews, grants and imports are scoped to it.
20. **Conflicts are deterministic.** Two active decisions in one project that give the same constraint key different values conflict (`jarvis_decision_conflicts`); an assistant's "this conflicts" is advisory. Replace supersedes in the same transaction; a cycle through depends_on is refused; a changed dependency raises a system proposal of type constraint_change and a receipt ("Book Flights Changed · Review 1 Dependent Decision"), never a rewrite.
21. **A withdrawn decision stays in the Decisions module.** Its item carries `withdrawnAt` and `withdrawnReason`; the module reads it as it always did. Reinstating is a new version through Replace.
22. **The Email tab keeps the app's own theme.** The redesign in place (slice 05) is drawn in the tokens every other tab wears and the approved mail row anatomy (`mail-rows.css`, Dave's picks of 2026-09-12), not section 02's cream palette: one tab bar, one palette, and the Hub's scoped island (deviation 17) is already the sample for Dave to judge the colour by. If he says yes to the cream, it is one scoped block for Email too.
23. **Provider reads moved to the server.** The old Email tab called Gmail from the browser with an access token the backend minted for it; the unified tab never holds one. Every read and every label change goes through `api/email/*` with the person's JARVIS session, the server mints the token from the stored sign-in and writes the cache with the service role, and the browser reads the cache with its own session through the row policies. Connecting, reconnecting and forgetting a mailbox stay where they were (Settings > Connections, `api/google.ts`), and `api/email/accounts.ts` mirrors those sign-ins into `email_account` rows.
24. **Remote images are off until asked.** Section 13 says no remote resource fetch; the app's sanitiser kept pictures because a picture is usually the point (Dave, 2026-09-02). Both hold: the unified tab asks the sanitiser for `remoteImages: false` (an http(s) picture loses its src, a stylesheet loses its https url(), inline and cid pictures stay) and offers Show Images on the message; the old tab's default is unchanged.
25. **Archive and trash receipts are the server's.** `jarvis_record` is not granted to the service role, and receipts are append-only, so `email_action_record` (0048) inserts the action and its first receipt itself, with Gmail's answer on the receipt and the command as the idempotency key (`archive_mail:<message>:<labels>`), after the provider confirmed and never before. Read and unread mirror a state and write no receipt. Unarchive is the Undo of an archive, untrash of a trash; there is no permanent delete.
26. **The category question is a row the person owns.** The spec's `policy_suggestion` row is offered by the browser on the third tap (`policy_suggestion_offer`, one open row per exact rule) and answered by Remember or Not Now (`policy_suggestion_answer`); the rule itself stays on the device (slice 02's decision).
