## Why there is a step 0

The JARVIS production database is not in the Supabase account this session can reach. That account holds two projects:
"Bridge-app" (the Bridge app's database) and "Bffsa Project", which has one table, `app_sync`, and no recorded migrations. So
this package cannot know which of the repo's migrations production already has. Step 0 is a read-only check that tells you;
apply only what it shows as missing, in number order.

## What the repo holds

`supabase/migrations/` holds 0001 to 0073, applied in number order. Two numbering facts to know: there is no 0070, and there are
two files numbered 0072 (`0072_email_signature_builder.sql` and `0072_table_originals.sql`). They touch different things and
either order is safe. Every migration from 0044 on has its exact inverse in `supabase/rollback/`.

## The one new migration: 0073, an event's person is a link

`migrations/0073_event_person_link.sql`, rollback `rollback/0073_event_person_link_down.sql`.

- **Why:** since 2026-10-27 an event carries a person (the event sheet's Person row, after "Text Josh Rudd"). The app writes it
  into `item.data.personId`, but the link registry `jarvis_link_paths()` (0060) does not list it, so `item_link` never shows an
  event's person. CLAUDE.md names this as needing a migration.
- **What it does:** replaces `jarvis_link_paths()` with 0060's exact list plus one row, `('event', 'personId', '$.personId',
  'about')`, and projects the event-person pointers that already exist, marked `operator` / `backfill_0073`.
- **What it does not do:** change any item, column, policy, grant or other function. No item row is written. No history row is
  written. The kind `about` is already allowed.
- **Proof, on a local Postgres 16:** `tests/event_person_link.sh`, 16 checks, all passing (forward twice, the trigger keeps it
  right on insert, change and removal, rollback, forward again).
- **Whole-chain rehearsal:** `tests/rehearsal.sh` was run with and without 0073. It reports the **same failures either way**
  (gateway 29, review 2, waiting 1, memory 2). Those come from proof scripts that main no longer matches, not from this
  migration; they are listed here so they are not mistaken for it. (memory.sh now leaves 0073 out of its pre-0060 chain, which
  it needs because 0073 calls a 0060 function.)
